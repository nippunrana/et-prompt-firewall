Baseline evaluation: what happened

Results of testing the Phase 1 firewall (rules + PIGuard + Prompt Guard 2, no LLM judge yet) on 3,124 public test texts. Firewall code frozen at commit 8b39d25, run on 30 September – 1 October 2026. Every number on this page is computed from the saved results. Hover a bar for exact counts.

The firewall notices most attacks, but it does not yet protect well. It raises far too many false alarms on normal email, it usually leaves most of the attacker's email in place when it cuts, and it rarely names the right attack type. These are the three problems Phase 3 (the LLM judge, whole-email removal and a re-check) has to fix. This baseline is the yardstick each fix will be measured against.

2. What we tested

Every text went through the firewall's own check, the same code the POST /check API runs: prepare the text, match rules, score with both classifiers, locate the attack, then allow, cut (sanitise) or hold (quarantine). The run recorded what was flagged, what was cut, which detector found it, and how long it took.

3. Attacks: noticed, but not removed

On the face of it, the firewall flags 80–100% of attacks. The unsafe-action families are low (about half), which is expected: they read as normal requests, and the tool-call guard is meant to handle them. The planted sets look perfect, but that is partly an illusion: PIGuard flags something in almost every inbox anyway (section 5).

Why “flagged” overstates protection. Every LLMail attack tries to make the AI email contact@contact.com. After the firewall cleans the text, that address is still there in about three quarters of the attacks. The firewall cuts a sentence or two, but an LLMail attack is a whole email written by the attacker, so most of it, including the instruction, stays in. (A surviving address is a strong warning sign, not proof the attack still works: sometimes the command is cut and only a mention remains.)

4. False alarms on normal email

Microsoft's short, clean emails are fine (3%). The harmless twins and real work emails are not: nearly half are flagged. The cause is clear from the data:

  • 96% of the false alarms on real work emails come from PIGuard alone, scoring a window of three sentences.
  • The longer the email, the worse it gets. The firewall scores every 3-sentence window (so that one bad line hidden in a long email is not diluted), and each extra window is another chance for PIGuard to misfire.
  • Most of what it wrongly cuts is tiny. 68% of PIGuard's wrong cuts in work emails are 8 words or fewer, and 48% are forwarded- or reply-email header lines such as “-----Original Message-----” or “Subject: FW: …”. Only an email's top header block is treated as one piece; headers quoted further down are split into short fragments, which PIGuard scores wildly high.

5. The two classifiers trade off

Both models scored every text. Neither is better in all respects:

PIGuard catches far more attacks but flags about half of normal email. Prompt Guard 2 almost never raises a false alarm but misses most attacks. The rules never misfire but catch only obvious phrasing. So the plan uses them differently: Prompt Guard 2 or a strong rule as confident evidence, and PIGuard alone as “suspicious: get a second opinion from the judge”, never as a reason to cut on its own.

6. Attack types: rarely named

The firewall flags most attack types well, but it rarely says which type. Neither classifier can name a type (each gives a single yes/no score); only the 14 rules name types, and they cover few techniques. The F-levels in the hackathon count the attack types detected, so naming types is the LLM judge's main job in Phase 3. Indirect injection is named whenever an attack is flagged, because every email counts as outside content.

The type labels on these 165 attacks were assigned by an AI labeller following a written guide and checked by a second, blind AI labeller (29 of 30 matched exactly). They were not checked by a human.

PIGuard's cut lands on the attack about 82% of the time, but it also cuts innocent text in nearly every inbox. Prompt Guard 2 and the rules almost never cut the wrong place, but they find under a third of the attacks. And even when the cut lands, it removes only about a quarter of the attacker's email.

9. Corrections made during testing

  • The first planted set was withdrawn. It inserted boundary-pair texts into emails. Some of them, such as “create a backdated approval entry… before the audit log updates”, read as ordinary (if shady) requests to a person once inside an email; only 4–12 of 50 texts in four families even address an AI. Those four families are now reported separately as unsafe-action requests (the tool-call guard's job), and the planted sets use real LLMail attacks proven to hijack an email assistant.
  • No self-written attacks. Attacks written by the people building the firewall would be weak evidence, so only public attacks are used.
  • A run was duplicated. Stopping a background run left its container running, so two runs wrote to one file. Every duplicated result matched exactly and was removed; runs now use a named container.
  • The rules were frozen first. The firewall code was fixed at 8b39d25 before the benchmark attacks were read in detail, so this baseline was not tuned on its own test data.

10. What it means for Phase 3

Problem foundPlanned fix
Half of normal email flagged, mostly by PIGuard on short fragmentsPIGuard alone never cuts: it sends the text to the LLM judge. Treat quoted forwarded/reply headers as one piece, like the top header.
Most of the attacker's email survives a sentence-level cutWhen an attack is found inside one email of an inbox or thread, remove or hold that whole email, then re-check what is left.
Attack types rarely namedThe LLM judge assigns the type.
Plain-request attacks and unsafe actions slip throughThe judge reads the user's actual request; the tool-call guard (Phase 4) blocks actions the user did not ask for.
Slow on long email (median 13 s for an LLMail email, much more for long threads)Skip the window drill-down when the whole text is clearly safe; measure on the server.

Rule for fair re-testing: any threshold or combination is chosen on one part of the data and reported on a separate, untouched part, so the improvement is not inflated by tuning on the test itself.

11. Glossary

TermMeaning
FlaggedThe firewall decided the text contains an attack (it cut something, or held the whole text).
Sanitise / cutRemove the attack and leave a visible marker; pass the rest on.
Quarantine / holdKeep the whole text back for a person to review.
RecallShare of attacks flagged. Higher is better.
False alarm / false-positive rateShare of normal texts wrongly flagged. Lower is better.
WindowThree consecutive sentences scored together.
PlantedAn attack placed at a known position inside normal email, so we can check where the cut lands.
CI (in the saved report)95% confidence interval: the range the true rate probably lies in, given the sample size.
