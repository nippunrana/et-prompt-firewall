# Demo UI and results dashboard

The Next.js app in `web/`: one guided "Try it" flow that starts with the input type in the hero (email opens the scenario, editable inbox and agents side by side; every other type runs the same two agents on one document or message, or is checked on its own, files included, with document extraction below it), results dashboard, audit log. The agent's ready-made scenarios live in `services/demo-agent/app/scenarios.py` and are served by `GET /scenarios`.

## Rules

- **Agent runs are background jobs, polled by the browser** (`POST /runs`, then `GET /runs/{id}` every 1.5 s). A protected run checks every email through the firewall and can take minutes on the VPS, longer than Cloudflare waits for one response (about 100 s). Never switch the UI back to the blocking `POST /run`; that endpoint stays for `eval/run_agent.py`.
- **Jobs live in the agent's memory** (the newest 50). A restart loses them; that is acceptable for a demo.
- **The dashboard only shows saved numbers.** `eval/report_heldout.py` writes `web/src/data/dashboard.json` from the saved runs; the server never runs a benchmark. After a new run, regenerate the file and rebuild `web`.
- **Never show a lucky run as typical.** Every scenario is measured several times by `eval/run_scenarios.py`; the dashboard shows those rates. The unprotected agent does not fall for every attack every time, so the video may need a retake.
- **Every browser `fetch()` starts with `BASE_PATH`** (Next.js does not add it to fetch).
- **Try it starts with the input type, from the problem statement's input sources, and that choice is the hero's only call to action** (user decisions, 2026-10-08/09, replacing the 2026-10-07 "no separate checker" rule; a separate "Any input" tab was tried and dropped because visitors landing on Try it never found it). Email leads as the full agent demo with measured scenarios; every other type runs the same two agents too (user decision, 2026-10-10, replacing "check one thing on its own") and can still be checked on its own. Email opens the inbox demo; the inbox stays mounted while another type is shown, so a running agent job keeps polling. The type decides the form (email fields, pasted text, file upload) and the firewall's front end; the detectors after it are shared, never a separate pipeline per type, because the measured reliability only carries over to the shared pipeline. Types without a dedicated front end (Markdown, API response, source code, OCR text) must say they are read as plain text. Email has no separate single-check form: the inbox's "Check this email" is it.
- **Try it shows one thing at a time, for the judges' demo** (user decision, 2026-10-09). Nothing is picked on load; picking an input folds the hero into a sticky bar and slides the form in, and clicking the bar reopens the hero to switch. Inside the email demo, the pick and the inbox show together with no "Next" button (user decision, 2026-10-09, replacing the one-step-at-a-time reveal): the first attack is already picked, its inbox is open below, and a run bar is fixed to the bottom of the window ("Run the AI orchestration"). The separate run step and its two-box checkpoint diagram were removed (user decision, 2026-10-09).
- **Try it has no nav tab; the logo is the way home** (user decision, 2026-10-09). It switches to the first view and reopens the hero through `HOME_EVENT` (`AppShell.tsx`, heard by `TryIt.tsx`), without resetting a running agent job. It is the only way back from Results or the audit log, so it must stay a real `<button>`, never a clickable `<span>`.
- **Never put a transform on an ancestor of the run drawer or the run bar.** Both are `position: fixed` inside the Try it panel, and a transform on an ancestor pins them to it instead of the window (the drawer once opened inside the page column). So the panel slides in with padding, not `y`, and the run bar sits outside the step sections. Never portal the run bar to `<body>`: it would escape the hidden tab and show over Results.
- **The drawer's checklist ticks a row only when its step has really happened** (`web/src/lib/pipeline.ts`): agent steps come from the job, and firewall stages come from `/check/stream`, relayed in the job's `live` field. "Running" means the step before it finished. Never tick ahead of an event or pace ticks on a timer; stages that land in one poll may stagger, within that poll.
- **The email demo's first step is "Pick an attack": one pick per technique, most common first, each with its share of attacks** (user decision, 2026-10-09, replacing "Pick a starting point"), so judges see which real threats are covered. The share comes from our labels of 165 working LLMail-Inject attacks (`eval/labels/`), computed into `dashboard.json` by `eval/report_heldout.py`; never type a share into the UI or quote it as an industry-wide rate. It is our labelling of one challenge, about ±7 points at this sample size: no published source gives prompt injection types by share for email (checked 2026-10-09: Microsoft's LLMail paper, CISPA's in-the-wild study, Pillar, Lakera, OWASP). The pick's "where it's caught" line is derived from the measured runs, never written by hand. Only the technique picks and "Blank inbox" are offered (user decision, 2026-10-09, dropping the "Also try" row); the task, missed-by-the-check and phishing scenarios stay in `scenarios.py`, unpicked, so the Results page keeps measuring the firewall's limits and that it lets normal mail through.
- **Every field of every email is editable, and testers can add their own** (up to the agent's 10-email limit). Once the inbox or request differs from the scenario, the run outcome only reports what the agent did: the scenario's attacker address no longer says whether an attack worked.
- **Two font families only: Geist and Geist Mono** (via `next/font`, no runtime font requests). Verdict colours (green, amber, red) mean allow, sanitise, block and are used for nothing else.
- **The agent's reply is rendered by `web/src/app/components/Markdown.tsx`, which builds React elements. Never render it as HTML** (no `dangerouslySetInnerHTML`, no Markdown library with raw HTML on): the reply can quote attacker-written email text.
- **Every input type runs the same two agents (`useAgentRuns.ts`, the same drawer); never build a second agent or a model-only comparison per type** (user decision, 2026-10-10). A document is read for the agent up front, like an attachment: left to the model, Qwen asked for the page instead of reading it in 5 of 6 live runs (2026-10-10), so the two runs differed in whether they read it at all. A pasted user message is the request itself, checked as the user's words before the model sees it; for it the guard is no defence (the user is the attacker), so the drawer must not imply one. A file's text is extracted once with its hidden ranges and sent with them, so the protected run's check matches "Check this file". These runs are unmeasured: the outcome reports only what each agent did (actions, guard blocks, a leaked canary), never a rate. Only the inbox stays mounted across type switches; another type's run stops polling when the type changes.
- **A blocked action is red, with a stop sign, and struck through; the protected run's headline stays green, with a shield** (user decision, 2026-10-10). Red marks the dangerous moment, green the outcome for the user: a red protected headline reads as "something went wrong" and loses the red-left, green-right contrast between the lanes. Icon shapes (stop sign, warning triangle, shield) carry the meaning as well as colour, for red-green colour-blind viewers. An action in the unprotected run turns red only on evidence: the protected run blocked the same action, its firewall cut the text naming the recipient, or the action carries the scenario's attacker address. Never on a guess: a tester's own request may really ask for it. Red is for these moments only; everything else stays ink.
- **Agent runs open in a right-hand drawer, and closing the drawer never cancels a run.** Polling lives in `AgentDemo`, not the drawer, so the run keeps going and "Watch the run" reopens it.
- **Every GSAP duration goes through `duration()` in `web/src/lib/motion.ts`,** which returns 0 for visitors who ask for reduced motion. Never animate with GSAP outside `useGSAP` (it cleans up on unmount), and never put a CSS `transform` on an element GSAP moves: GSAP reads it as a pixel offset and the drawer ends up off screen.
- **The layer track (`LayerTrack.tsx`, `web/src/lib/layers.ts`) never draws a layer that did not run like one that passed.** On clean emails the judge and sandbox are skipped by design, and without an API key they are unavailable; both are dashed and labelled. A "passed" dot for a layer that never ran would be a false claim to the judges.
- **Track dots use ink tones only (solid, ringed, hollow, dashed), never verdict colours** (user decision, 2026-10-08). A layer flag is not a block: the judge can clear it.
- **The track's dot-to-dot travel is a replay of one `/check` answer, paced by its `trace` timings.** Never present it as live progress.
- **The hero's first row is a full-width band: headline, a quiet diagram (`HeroDiagram.tsx`) and the email demo as its button, never the looping card** (user decisions, 2026-10-09, replacing the card beside the headline): moving text next to the headline competed with it, and a hard band edge is what makes the hero read as its own section. The full input choice sits below the band edge, and the simulation below that, inside the fold, so both fold away once an input is picked. The proof line reads `dashboard.json`; never type numbers into it.
- **The hero's fold box spans the whole window, so its `overflow: hidden` clips at the window edges, not the page column** (`hero.module.css`; `body` has `overflow-x: clip` for the scrollbar's overshoot). Never let the band bleed out of a page-column-wide fold with one-axis clipping (`overflow-x: visible; overflow-y: clip`): a browser on the Mac clipped both axes while GSAP faded the fold, and the band split in two on every pick and reopen.
- **The hero's looping card (`HeroSimulation.tsx`) is the one place where ticks follow a timer, and only because it is labelled a simulation** (user decision, 2026-10-09). It runs scripted example emails through the drawer's own checklist milestones (same step names and wording, from `lib/pipeline.ts`), with Checkpoint 1 summarizing its 9 detection stages via a compact segmented mini-track and dynamic ticker so visitors learn the architecture without first-fold cognitive overload. Once a run finishes, it holds for 5 seconds with an animated reverse countdown ring and counter before starting the next scenario (user decision, 2026-10-09). Never feed it from a real job, and never drop the "simulation" label. Its only real numbers come from `dashboard.json`: a static "~14 ms latency, 99.4 % detection" line that nothing measured was removed from the hero, and must not come back. **The card keeps one height through the whole loop** (user decision, 2026-10-09): every slot whose text changes goes through `Steady`, which reserves room for its longest variant. Text added outside it makes the card, and the hero, jump between steps.
- **The hero's interactive controls never use `aria-pressed`, apart from the input choices.** Reopening the hero focuses the first `[aria-pressed="true"]` inside it (`TryIt.tsx`), so the simulation's example tabs use `aria-current`.
