Prompt Injection Firewall: architecture

What is built today, how content flows through it, and what is still planned. ET AI Hackathon, Problem 2. Current state as of 30 September 2026 (firewall code at commit 8b39d25, evaluation harness at 0f5852b).

The firewall is a separate service that reads every piece of incoming content before an AI agent sees it. It finds hidden instructions, names their attack type, cuts them out, and passes the rest through. 2. The whole system

Content comes in from three kinds of source. Documents are first turned into text. Everything then goes through /check, which returns a verdict and a cleaned copy. In the finished system the agent only ever reads the cleaned copy, and its tool calls pass a second checkpoint.

Three separate services

firewall (Python, FastAPI) is the product. demo-agent (Python) is the thing it protects in the demo. web (Next.js) is the user interface. They run as separate containers on purpose: the firewall stands alone as an API, which is the claim the architecture makes.

Why the agent reads only the firewall's output

If the agent could also read the raw email, a missed attack would reach it anyway, and a caught one might too. Routing everything through /check makes the firewall the only path in.

3. Inside /check

This is the core flow, taken from the code. Every step records its timing in a trace, so the result shows how the decision was reached.

1 · PrepareMakes hidden text visible without losing where each character came from: normalises Unicode, strips invisible characters, maps look-alike letters (Cyrillic "а" → "a", only inside Latin words), joins s p a c e d letters, and decodes Base64, hex and invisible-Unicode payloads, up to two layers deep. Then it splits the text into units (sentences and lines). An email's header block is one unit, so short header lines don't get unreliable scores of their own.
2 · RulesPrecise, explainable patterns for known attack phrasing. A strong rule is evidence on its own ("ignore all previous instructions"). A weak rule is only a hint, because the same words are normal in email ("please send the report to…"). A weak hint joins a cut only when it sits next to real evidence.
3 · ClassifiersBoth models score the whole text (in 512-token windows) and every run of three units. No window is skipped because the whole text looked fine: one bad line inside a long friendly email scores low overall.
4 · LocateFor every high window: compare its two overlapping pairs, then the single units, and cut the smallest piece that explains the score. A single sentence can locate an attack but never trigger a cut by itself, because short fragments get wild scores (a subject line once scored 1.0).
5 · Collect and decideSpans from the classifiers, strong rules and decoded payloads are merged. Any span means sanitise: cut it and leave a visible marker. Flagged as a whole but impossible to pin down means quarantine. Otherwise allow.
6 · ReportThe lane says how sure it is: clean, clear attack (a strong rule and a classifier agree) or unsure. In Phase 3 the unsure lane goes to the LLM judge.
Planned · Re-check, judge, human reviewThe cleaned text is checked again and the cut widened at most twice; if it still isn't clean, the content is quarantined for a person to review.
Fail closed. If the classifiers fail, the check still runs on the rules alone and says so in warnings. It never passes text unchecked. A missing source is treated as outside content, never as the user.

5. Design decisions already made

DecisionWhy
Detection never changes by source; source only names the type (an attack in outside content is also indirect injection)An attacker controls the content, not the label. Treating email as "less trusted" would make the same text pass in chat.
Sanitise by default; cuts are always visible; quarantine only when cutting can't be trustedLegitimate content keeps flowing, and a person can see exactly what was removed.
Drill-down localisation over every window; single sentences only locateAvoids both dilution (a bad line hidden in a long email) and false alarms from short fragments.
Two classifiers from the start, combined by measured dataPIGuard catches more planted instructions but over-flags instruction-heavy normal text; Prompt Guard 2 rarely false-alarms but misses plain requests. The evaluation decides how to combine them.
If the simulation detector is adopted, its verdict comes from code checks on the model's tool calls, never from another model reading its outputA hijacked model writes attacker-controlled text, which could steer a second model.
Never claim the firewall is unbreakablePublished adaptive attacks beat every tested defence; the demo shows one we miss.

Honesty rules built in: no set is in PIGuard's training data; results are reported per template family and per team, not only per email; LLMail type labels were made by an AI labeller and checked by a second, blind one (29/30 exact), not by humans; credential theft has no clean public set and will be shown through the tool-call guard.

7. Deployment

Images are built only by GitHub Actions on x86_64 and pulled by the server; the server never builds. Every service has CPU and memory caps because the server is shared with live applications. A deploy that fails its health checks rolls back to the previous images automatically (tested on purpose). Nothing is pushed without the owner's approval, because a push to main deploys.
